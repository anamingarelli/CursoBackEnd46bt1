## LISTA DE EXERCÍCIOS DE FIXAÇÃO E PRÁTICA - SESSÕES, COOKIES e AUTENTICAÇÃO DE USUÁRIOS

### Parte A: Exercícios Teóricos de Fixação

#### 1. **Protocolo Stateless:** O que significa afirmar que o protocolo HTTP é "stateless" e por que o mecanismo de cookies/sessões é necessário para aplicações modernas?

- R: O protocolo HTTP ser stateless significa que o servidor **não guarda memória das requisições anteriores**, tratando cada clique como o de um usuário inédito. Os cookies e sessões são necessários para contornar isso: a sessão guarda os dados do usuário no servidor, e o cookie salva um identificador no navegador. O navegador envia esse cookie a cada nova requisição, permitindo que a aplicação reconheça quem você é e te mantenha logado.

#### 2. **Cookies vs. Sessões**: Qual é a diferença entre os dados armazenados em um cookie e os dados mantidos no array superglobal `$_SESSION`? Qual dos dois apresenta maior segurança para informações confidenciais?

- R: A principal diferença é o *local de armazenamento*: os dados de um cookie ficam salvos no navegador do cliente, enquanto os dados do `$_SESSION` ficam guardados no servidor. A `$_SESSION` **apresenta maior segurança** para informações confidenciais. Como seus dados ficam trancados no servidor, o usuário não pode visualizá-los ou modificá-los diretamente. Já os cookies podem ser facilmente interceptados, alterados ou lidos por terceiros no navegador, sendo inadequados para dados sensíveis como senhas ou dados pessoais.

#### 3. **A Flag HttpOnly**: Explique detalhadamente como a configuração `httponly => true` impede o sequestro de sessão (Session Hijacking) mesmo se a aplicação possuir uma vulnerabilidade de Cross-Site Scripting (XSS).

- R: A configuração `httponly => true` impede o sequestro de sessão bloqueando o acesso aos cookies via JavaScript. Em um ataque de **Cross-Site Scripting (XSS)**, o invasor injeta códigos maliciosos na página para ler os cookies do usuário usando o comando `document.cookie`. Com a flag ativa, o navegador *proíbe o JavaScript de acessar esse cookie*, retornando um valor vazio. O cookie continua sendo enviado automaticamente ao servidor nas requisições HTTP, mas o hacker não consegue capturar o ID de sessão, impossibilitando que ele roube a identidade da vítima de outro computador.

####  4. **A Flag SameSite**: Qual é a finalidade do atributo ` SameSite=Lax` em cookies e contra qual tipo de ataque corporativo ele atua?

- R: A finalidade do atributo `SameSite=Lax` é *controlar o envio de cookies em requisições feitas a partir de sites externos*, atuando diretamente contra o ataque de **CSRF (Cross-Site Request Forgery / Falsificação de Requisição Entre Sites)**. Com essa configuração, o *navegador bloqueia o envio automático do cookie* se a requisição partir de um site terceiro (como um link malicioso oculto em um e-mail ou imagem). O cookie só é enviado se o usuário realizar uma navegação segura de alto nível, como clicar em um link normal que o leve diretamente para o site de origem. Isso impede que um invasor force o navegador da vítima a executar ações indesejadas (como transferências bancárias ou alteração de dados corporativos) aproveitando-se de uma sessão já aberta.

#### 5. **Ataque de Fixação de Sessão**: O que é o ataque de Session Fixation e por que é mandatório executar `session_regenerate_id(true)` imediatamente após o login do usuário?

- R: O ataque de **Session Fixation (Fixação de Sessão)** ocorre quando *um invasor escolhe e força um ID de sessão válido no navegador da vítima* (por exemplo, enviando um link com o ID na URL). Quando a vítima faz o login usando esse ID já conhecido, o servidor valida a sessão, permitindo que o hacker acesse a conta invadida usando o mesmo identificador. A execução do `session_regenerate_id(true)` imediatamente após o login é mandatória porque ela destrói o ID de sessão antigo e cria um totalmente novo no momento em que o usuário se autentica. Isso garante que, mesmo se o invasor tiver fixado um ID no navegador da vítima antes do login, esse ID antigo se tornará inválido e inútil, neutralizando completamente o ataque

#### 6. **MD5 e Rainbow Tables**: Por que é considerado negligência técnica armazenar senhas com algoritmos rápidos como `MD5` ou `SHA256`? Como as *Rainbow Tables* operam contra esses hashes?

- R: Armazenar senhas com algoritmos rápidos como `MD5` ou `SHA256` é considerado negligência técnica porque eles foram projetados para integridade de arquivos, e não para senhas. Por serem extremamente velozes, um computador comum consegue testar bilhões de hashes por segundo, tornando ataques de força bruta ou dicionário quase instantâneos em caso de vazamento do banco de dados. As Rainbow Tables operam contra esses hashes funcionando como tabelas de busca pré-computadas. Em vez de adivinhar a senha na hora, o invasor usa essas tabelas que contêm milhões de senhas comuns e seus respectivos hashes já calculados de forma compactada. Diante de um hash MD5 ou SHA256 exposto, o hacker faz apenas uma busca rápida na tabela para reverter o hash e descobrir a senha original em segundos.

#### 7. **O Papel do Salt**: O que é o Salt criptográfico e por que ele garante que dois usuários com a mesma senha possuam hashes completamente distintos no banco de dados?

- R. **O Salt criptográfico** é uma sequência de caracteres aleatórios gerada automaticamente pelo sistema e adicionada à senha do usuário antes de realizar a criptografia (gerando o hash). Ele garante hashes completamente distintos para a mesma senha porque **o Salt é único para cada usuário**. Quando dois usuários escolhem a mesma senha *(ex: "123456")*, o sistema combina cada uma com um Salt diferente antes de gerar o hash. Como o dado de entrada final se torna diferente para cada conta, os hashes resultantes no banco de dados serão totalmente diferentes. Isso impede que um invasor descubra senhas duplicadas em massa e inutiliza o uso de Rainbow Tables, já que os hashes pré-computados não corresponderão aos hashes com Salt do sistema.

#### 8. **Argon2id vs Bcrypt**: Por que o algoritmo Argon2id é considerado superior ao Bcrypt na proteção contra ataques de força bruta realizados por placas de vídeo (GPUs) e circuitos ASIC? 
- R: O algoritmo Argon2id é considerado superior ao Bcrypt porque ele é "memory-hard", o que significa que ele exige uma grande quantidade de memória RAM para calcular um único hash, além do poder de processamento. Placas de vídeo (GPUs) e circuitos ASIC possuem milhares de núcleos de processamento que executam tarefas em paralelo de forma ultraveloz. O Bcrypt exige apenas poder de processamento bruto, permitindo que esses hardwares especializados testem milhões de senhas por segundo. O Argon2id neutraliza essa vantagem ao forçar cada tentativa a ocupar um bloco configurável de memória RAM. Como as GPUs e ASICs possuem pouca memória dedicada por núcleo, elas sofrem um gargalo de memória, tornando os ataques de força bruta paralelos inviáveis e extremamente caros.

#### 9. **Timing Attacks**: Por que a verificação de senhas deve ser feita com `password_verify()` em vez do operador de comparação comum `===`?
- R: A verificação de senhas deve ser feita com `password_verify()` porque ela utiliza um algoritmo de comparação em tempo constante, blindando a aplicação contra ataques de tempo (Timing Attacks). O operador comum `===` compara textos caractere por caractere e interrompe a operação no primeiro erro. Se a senha correta começa com "A" e o invasor testa "B", o sistema rejeita o teste instantaneamente; se ele testa "A", o sistema demora um milionésimo de segundo a mais para analisar o próximo caractere. Medindo essa diferença milimétrica de tempo de resposta do servidor, um hacker consegue adivinhar a senha caractere por caractere. A função `password_verify()` sempre leva exatamente o mesmo tempo para responder, independentemente de quantos caracteres estejam certos ou errados. Isso impede que o invasor use o tempo de processamento para obter pistas sobre a senha.
