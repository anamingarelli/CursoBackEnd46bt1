# LISTA DE EXERCÍCIOS DE FIXAÇÃO E PRÁTICA - MVC

## Parte A: Questões Teóricas de Fixação

### **1. O Colapso do Código Espaguete:** Explique por que manter consultas SQL, regras de validação e marcação HTML no mesmo arquivo inviabiliza a manutenção e a escalabilidade de um sistema corporativo.

R: Misturar SQL, HTML e validações no mesmo arquivo cria um acoplamento direto: alterar o visual pode derrubar o banco de dados e vice-versa.

Exemplo: Em um arquivo `produto.php` que contém `SELECT * FROM produtos` misturado com tags `<table>`, alterar a cor de uma coluna exige editar o mesmo arquivo que manipula o banco. Se você cometer um erro de digitação no HTML ou esquecer um ponto e vírgula, a consulta SQL para de funcionar. Além disso, é impossível testar a consulta sem carregar o HTML todo na tela.

### **2. A Tríade MVC:** Qual é a função específica de cada um dos três componentes do padrão MVC (Model, View, Controller)? Qual deles deve conter as regras de negócio?

R: No padrão arquitetural MVC, a aplicação é dividida em três camadas com atribuições bem delimitadas. O Model é o componente responsável pela representação do domínio, gerenciamento do estado da aplicação, persistência de dados no banco e validação das entidades; é no Model que devem residir exclusivamente todas as regras de negócio do sistema. A View atua de forma passiva, sendo responsável unicamente pela apresentação gráfica da resposta ao usuário (seja em HTML, CSS ou JSON), sem tomar decisões operacionais ou realizar consultas diretas. O Controller atua como um intermediário ou orquestrador do fluxo da requisição: ele recebe o estímulo HTTP enviado pelo cliente, extrai os parâmetros necessários, aciona os métodos correspondentes no Model para executar a lógica de negócio e, por fim, seleciona a View adequada, repassando os dados necessários para que a resposta seja renderizada.

### **3.O Papel do Composer:** Diferencie o papel do arquivo `composer.json` do arquivo `composer.lock`. Por que a pasta `vendor/` nunca deve ser versionada no Git?

R: No ecossistema PHP, o arquivo composer.json atua como o manifesto de configuração do projeto, no qual são declaradas as dependências diretas de terceiros, as restrições de versões aceitas, os metadados do projeto e as regras de carregamento automático de classes via PSR-4. Por sua vez, o arquivo composer.lock funciona como um registro exato e imutável do estado da instalação, armazenando os hashes e as versões precisas de cada biblioteca e subdependência instaladas no momento em que o comando de atualização foi executado. Essa distinção garante que todos os ambientes de desenvolvimento, homologação e produção utilizem rigorosamente o mesmo código-fonte. A pasta vendor/ jamais deve ser versionada no Git porque contém milhares de arquivos de terceiros redundantes que podem ser reconstruídos a qualquer momento executando o comando composer install com base no composer.lock. Subir essa pasta incharia o repositório, poluiria o histórico de commits e poderia causar incompatibilidades, pois certas bibliotecas geram arquivos nativos específicos para o sistema operacional onde foram baixadas.

### **4. A Especificação PSR-4:** Como o Autoloader PSR-4 consegue localizar o arquivo `src/Controllers/ProdutoController.php` a partir do namespace `App\Controllers\ProdutoController`?

R: A especificação PSR-4 padroniza o carregamento automático (autoloading) de classes mapeando prefixos de namespaces PHP diretamente para caminhos no sistema de arquivos. Quando o arquivo composer.json estabelece que o namespace raiz App\ aponta para o diretório src/, o autoloader do Composer intercepta a chamada de instanciação da classe App\Controllers\ProdutoController e executa um algoritmo de resolução de caminho. Primeiro, o prefixo App\ é identificado e substituído pelo diretório base src/. Em seguida, os separadores de namespace em barra invertida (\) presentes no restante do nome (Controllers\ProdutoController) são convertidos para as barras de diretório do sistema operacional (/), resultando em Controllers/ProdutoController. Por fim, o autoloader anexa a extensão .php ao final da string e executa a inclusão automática do arquivo localizado em src/Controllers/ProdutoController.php por meio de uma instrução require_once interna.

#### **5. Front Controller:** Qual é a principal vantagem de segurança ao centralizar todas as requisições em `public/index.php` e isolar os arquivos-fonte do projeto fora da raiz pública da web?

R: A arquitetura de Front Controller traz uma vantagem fundamental de segurança ao centralizar a entrada de todas as requisições HTTP em um único arquivo, o public/index.php. O servidor web (Apache ou Nginx) é configurado para definir a pasta public/ como a raiz pública (Document Root). Como os arquivos-fonte da aplicação (src/), dependências (vendor/) e configurações com dados sensíveis (.env) ficam armazenados um nível acima do diretório público, torna-se impossível para um usuário malicioso acessá-los diretamente através da URL, resultando em erros de acesso (404/403). Além do isolamento físico, ter um ponto de entrada único obriga todas as chamadas a passarem por um fluxo centralizado, permitindo a execução uniforme de rotinas globais de segurança antes de qualquer processamento, como verificação de autenticação, validação de tokens CSRF, sanitização de dados de entrada e tratamento centralizado de exceções.

### **6. Roteador HTTP:** Como o objeto `Roteador` diferencia uma requisição `GET /produtos` de uma requisição `POST /produtos`?

R: O objeto Roteador diferencia requisições enviadas para uma mesma URI inspecionando as variáveis de ambiente disponibilizadas pelo servidor web na superglobal `$_SERVER`, especificamente o verbo HTTP contido em `$_SERVER`
`['REQUEST_METHOD']` e o caminho da URL em `$_SERVER`
`['REQUEST_URI']`. O roteador mantém uma tabela interna de rotas mapeada por essas duas informações. Quando o sistema recebe a requisição GET /produtos, o roteador identifica o verbo GET e direciona a chamada para o método do Controller responsável pela listagem e exibição do catálogo. Quando a requisição é um POST /produtos, o roteador reconhece o verbo POST como uma intenção de envio de dados e direciona o fluxo para o método do Controller responsável pelo processamento do formulário e salvamento no banco de dados.


### **7. Injeção de Dados na View:** Como a função nativa `extract()` atua no método `renderizar()` do Controller para disponibilizar variáveis para as Views?

R: No método renderizar() do Controller, a função nativa extract() é utilizada para importar as chaves de um array associativo de dados diretamente para a tabela de símbolos do escopo local. Quando o Controller passa um array como `['produtos' => $lista, 'titulo' => 'Catálogo']`, a chamada ao extract() cria automaticamente as variáveis locais $produtos e $titulo dentro do método. Como a inclusão do arquivo da View é feita logo na sequência utilizando a instrução require dentro dessa mesma função, a View é executada herdando exatamente esse mesmo escopo local. Dessa forma, dentro do arquivo da View é possível acessar e exibir os dados diretamente através de variáveis simples como $produtos e $titulo, sem a necessidade de manipular arrays genéricos.

### **8. Segurança contra XSS nas Views:** Por que todas as saídas dinâmicas exibidas em tabelas e formulários devem ser envolvidas com `htmlspecialchars()`?

R: Todas as saídas dinâmicas exibidas em tabelas e formulários devem ser tratadas com a função htmlspecialchars() para prevenir ataques de Cross-Site Scripting (XSS). O ataque XSS ocorre quando dados inseridos por usuários contêm scripts maliciosos em JavaScript ou marcações HTML que acabam sendo armazenados no banco de dados e posteriormente executados pelo navegador de outros usuários. Ao aplicar a função htmlspecialchars() antes da exibição de qualquer variável, o PHP converte os caracteres reservados da sintaxe HTML (como os sinais de menor, maior, aspas e e-comercial) em suas respectivas entidades de texto inofensivas. Com essa conversão, se um usuário injetar a tag `<script>alert('hack')</script>`, o navegador interpretará o conteúdo estritamente como texto puro a ser impresso na tela (`&lt;script&gt;...`), anulando completamente a capacidade de execução do código malicioso.


### **9. Single Responsibility no Controller:** Por que um Controller nunca deve conter comandos SQL com strings concatenadas ou conexões diretas via `new PDO()`?

R: Um Controller nunca deve conter comandos SQL com strings concatenadas nem instanciar conexões diretas via new PDO() por três razões fundamentais. A primeira é a violação do Princípio da Responsabilidade Única (SRP): a função do Controller é orquestrar o tráfego HTTP, cabendo exclusivamente à camada de Model gerenciar a infraestrutura e a persistência no banco de dados. A segunda razão é a segurança, pois a concatenação de strings em comandos SQL expõe o sistema a ataques graves de SQL Injection; o acesso aos dados deve ser isolado no Model através de consultas preparadas (Prepared Statements). A terceira razão é a testabilidade: instanciar a conexão diretamente dentro do Controller cria um acoplamento rígido com o banco de dados real, o que impede a execução de testes unitários isolados, nos quais o banco precisaria ser substituído por objetos simulados (mocks).


### **Transição para o Framework Laravel:** Identifique quais conceitos aprendidos neste MVC artesanal são exatamente os mesmos utilizados pelo Laravel 11.

R: Os conceitos fundamentais desenvolvidos no estudo do MVC artesanal são mantidos e aprimorados no framework Laravel 11. O Laravel utiliza rigorosamente o padrão Front Controller, tendo o arquivo public/index.php como o ponto central de entrada para todas as requisições. O carregamento de classes segue a especificação PSR-4 via Composer, mapeando a estrutura de diretórios dentro do `namespace App\`. O roteamento em routes/web.php diferencia explicitamente as requisições por meio dos verbos HTTP e das URIs declaradas. A separação de responsabilidades é mantida através do ORM Eloquent nos Models, preservando os Controllers como orquestradores enxutos. A passagem de dados para as interfaces ocorre de forma análoga à função extract(), utilizando o ajudante view() com compact(). Por fim, a proteção contra ataques XSS é aplicada nativamente pelo motor de templates Blade, que executa o equivalente ao htmlspecialchars() automaticamente sempre que a sintaxe de interpolação {{ $variavel }} é utilizada.
